# Profyl.dev

**A living developer profile built from your engineering work.**

Profyl brings together signals from GitHub, LeetCode, and featured projects into one shareable developer profile.

Instead of maintaining a static portfolio alongside separate GitHub, LeetCode, and resume links, Profyl turns existing engineering activity into a profile that can evolve with the developer.

## Overview

Profyl combines three things:

* **Aggregation** of developer activity from connected sources
* **Analysis** through deterministic engineering signals
* **Interpretation** through AI-generated insights

A published profile includes a **Profyl Score**, **Specialization Radar**, quantified GitHub and LeetCode metrics, featured projects, and AI-generated summaries.

The goal is not to measure engineering ability objectively. It is to make observable technical work easier to understand.

---

## Highlights

### Multi-source developer signals

GitHub and LeetCode provide different types of evidence, so Profyl keeps their signals separate before combining them.

The current Specialization Radar covers:

* Build Activity
* Technical Range
* Problem Solving
* Consistency
* Open Source

The overall Profyl Score is derived from normalized signals rather than generated by an LLM.

### Deterministic repository analysis

Featured GitHub repositories are analyzed using repository evidence rather than relying entirely on AI.

The analysis pipeline:

```text
Repository
    ↓
File Tree
    ↓
Manifest Discovery
    ↓
Dependency Parsing
    ↓
Technology Detection
    ↓
Capability Mapping
    ↓
Technical Profile
```

The current repository analyzer supports four major ecosystems:

- JavaScript / TypeScript
- Java
- Python
- Go

Supported manifests include ecosystems such as:

```text
package.json
requirements.txt
pyproject.toml
pom.xml
build.gradle
go.mod
```

Detected technologies are normalized through a central registry and mapped to broader capabilities such as databases, authentication, caching, AI/ML, infrastructure, and real-time systems.

This keeps **technology detection, capability detection, and scoring** as separate concerns.

### AI as an interpretation layer

AI does not calculate Profyl scores or decide which technologies are present.

Instead:

```text
External Data
     ↓
Normalized Data
     ↓
Repository Analysis
     ↓
Deterministic Analytics
     ↓
AI Context
     ↓
AI Interpretation
```

The AI layer uses structured signals and project context to produce developer and project summaries.

This makes the quantitative layer deterministic while using AI where it adds the most value: synthesizing information that would otherwise require manual interpretation.

At a high level:

```text

                   │
                   ▼

                   │
                   ▼
             Cached Source Data
                   │
          ┌────────┴────────┐
          ▼                 ▼
 Repository Analysis    LeetCode Data
          │                 │
          └────────┬────────┘
                   ▼
            Analytics Engine
                   │
          ┌────────┴────────┐
          ▼                 ▼
      Profyl Score     Specialization
                       Radar
          │                 │
          └────────┬────────┘
                   ▼
            AI Interpretation
                   │
                   ▼
             Public Profile
```

The application separates:

* External integrations
* Data synchronization
* Repository analysis
* Analytics
* AI generation
* Profile rendering
* Persistence

This keeps external API logic out of the UI and prevents derived analytics from becoming coupled to individual integrations.

## Data & Synchronization

External platform data is persisted in PostgreSQL rather than fetched during every profile request.

Profyl uses a cache-first, stale-while-revalidate approach:

```text
Request
  ↓
Cached Data
  ├── Fresh → Return
  │
  └── Stale → Return + Refresh
                     ↓
                  Re-sync
                     ↓
               Recompute signals
```

This keeps public profile rendering independent of third-party API latency and allows the application to serve the last known good data when an external service is temporarily unavailable.

GitHub repository synchronization uses a snapshot model. Public, non-forked, non-archived repositories are synchronized into the current repository state, while user-specific profile configuration remains separate from GitHub-owned metadata.

## Analytics

Profyl's scoring layer is deterministic.

Each signal has its own calculation and normalization before being consumed by the aggregation layer.

Examples:

**Build Activity**

Measures observable building activity through contribution volume and active projects.

**Technical Range**

Measures breadth of engineering capabilities detected across featured repositories.

**Problem Solving**

Combines LeetCode problem volume, difficulty distribution, and contest performance.

**Consistency**

Measures activity patterns across GitHub and LeetCode.

**Open Source**

Combines merged external contributions with repository-level external impact.

The system also distinguishes between **zero** and **unavailable** data so missing external information does not automatically become a negative signal.

Profyl uses a self-hosted fork of [`alfa-leetcode-api`](https://github.com/alfaarghya/alfa-leetcode-api) to fetch LeetCode data through GraphQL.

## Project Structure

The codebase is organized around the Next.js App Router, with application logic, external integrations, analytics, and UI components separated into focused modules.

```text
src/
├── app/                         # Next.js App Router pages and API routes
│   ├── [slug]/                  # Public profile pages
│   ├── api/                     # API endpoints and webhooks
│   │   ├── public-profile/      # Public profile APIs and refresh logic
│   │   └── webhooks/            # External webhook handlers
│   ├── dashboard/               # Profile management and project dashboard
│   ├── docs/                    # Scoring and methodology documentation
│   ├── onboarding/              # Onboarding and project selection
│   ├── (auth)/                  # Authentication routes
│   ├── layout.tsx               # Root layout and providers
│   └── page.tsx                 # Landing page
│
├── components/                  # React UI components
│   ├── ui/                      # Reusable UI primitives
│   ├── profyl/                  # Public profile components
│   ├── dashboard/               # Dashboard components
│   ├── onboarding/              # Onboarding components
│   ├── leetcode/                # LeetCode components
│   └── docs/                    # Documentation components
│
├── lib/                         # Business logic and infrastructure
│   ├── ai/                      # AI generation and prompt logic
│   ├── analytics/               # Developer evaluation and scoring
│   │   ├── repository-analysis/ # Repository scanning and tech detection
│   │   └── scoring/             # Signal scoring modules
│   ├── services/                # GitHub, LeetCode, analytics and freshness services
│   ├── github/                  # GitHub API client and normalizers
│   ├── leetcode/                # LeetCode API client and normalizers
│   ├── auth/                    # Authentication helpers
│   ├── errors/                  # Application-specific errors
│   └── webhooks/                # Webhook processing
│
├── styles/                      # Global styles and design tokens
├── types/                       # TypeScript definitions and interfaces
└── proxy.ts                     # Middleware / proxy handler

```

The application uses **Server Components for reads**, **Server Actions for mutations**, and **Route Handlers for HTTP endpoints and webhooks**, with shared business logic kept within the `lib/` layer.

The exact structure may evolve, but the intended dependency flow is:

```text
Request Boundaries
(Server Components / Server Actions / Route Handlers)
                         ↓
                   Service Layer
                    ↙         ↘
          External Clients    Prisma
                 ↓               ↓
          External APIs      PostgreSQL
                                ↓
                         Domain / Analytics
                                ↓
                                AI
```

Request boundaries remain thin, while services own business logic and orchestration. External clients handle communication with third-party systems, Prisma handles persistence, and analytics operates on normalized persisted data.

## Engineering Principles

A few principles guided the MVP:

**Deterministic where possible**
Scoring and technical capability detection do not depend on AI.

**Evidence over claims**
Repository evidence is preferred over README-only or user-declared claims for technical analysis.

**Derived data stays derived**
Analytics and AI insights are generated from persisted source data rather than becoming independent sources of truth.

**Missing is not zero**
Unavailable external data is distinguished from genuine zero activity.

**Simple infrastructure**
The MVP uses PostgreSQL-backed caching and request-triggered refreshes instead of introducing queues, Redis, or worker infrastructure without a demonstrated need.

**One profile renderer**
The dashboard preview and public profile use the same profile rendering system, reducing divergence between what a developer edits and what others see.

## Running Locally

### Requirements

* Node.js
* PostgreSQL
* Clerk application
* GitHub OAuth configuration
* LeetCode API service
* AI provider credentials

### Setup

```bash
git clone <repository-url>
cd profyl
npm install
```

Create your environment file:

```bash
cp .env.example .env.local
```

Configure the required environment variables and run the database migrations:

```bash
npx prisma migrate dev
```

Start the development server:

```bash
npm run dev
```

## Why I Built It

Developer work is increasingly distributed across platforms, but the way that work is presented is still largely static.

Profyl explores a different model: a developer profile that is built from observable work and can evolve as that work changes.

The interesting engineering challenge is turning heterogeneous external data and repositories with different structures and technology stacks into a consistent, explainable representation. Profyl's repository analysis and technology detection are designed to work reliably across a wide range of project layouts and ecosystems, without making an LLM responsible for the parts of the system that should remain deterministic.
